# 2. Persistent Volumes & Claims

> 앞선 볼륨에서는 스토리지 설정을 Pod 정의 파일 안에 직접 넣었다.
> 하지만 사용자, Pod가 많아지면 매번 모든 Pod에 스토리지를 설정하고 변경해야 해서 번거롭고 오류가 잦다.
> PV와 PVC는 스토리지를 중앙에서 관리하도록 이 문제를 해결한다.

---
## 1. PV와 PVC의 개념
- **PersistentVolume (PV)**: 관리자(admin)가 미리 만들어 두는 클러스터 전체의 스토리지 풀. 큰 스토리지를 만들어 둔다.
- **PersistentVolumeClaim (PVC)**: 사용자(user)가 그 풀에서 필요한 만큼을 잘라내어 요청하는 오브젝트.

> 관리자는 PV 세트를 만들고, 사용자는 PVC를 만들어 스토리지를 사용한다.

---
## 2. PV 만들기
- `apiVersion: v1`, `kind: PersistentVolume`
- `accessMode`: 볼륨을 어떻게 마운트할지 정의. 지원값: `ReadOnlyMany`, `ReadWriteOnce`, `ReadWriteMany`
- `capacity.storage`: 예약할 용량(ex. 1Gi)
- 볼륨 타입: 데모에서는 `hostpath`로 시작

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-vol1
spec:
  accessModes:
    - ReadWriteOnce
  capacity:
    storage: 1Gi
  hostPath:
    path: /tmp/data
```

> `hostPath`는 데모/테스트 전용. 프로덕션 환경에서는 권장 x

```bash
kubectl create -f pv-definition.yaml
kubectl get persistentvolume
# NAME      CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS   AGE
# pv-vol1   1Gi        RWO            Retain           Available                          3m
```

**클라우드 스토리지 백엔드 사용**
프로덕션에서는 `hostPath`대신 클라우드 스토리지를 쓴다. `hostPath`필드를 `awsElasticBlockStore` 등으로 바꾸자.

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-vol1
spec:
  accessModes:
    - ReadWriteOnce
  capacity:
    storage: 1Gi
  awsElasticBlockStore:
    volumeID: <volume-id>
    fsType: ext4
```

> `awsElasticBlockStore`는 현재 deprecated된 상태이다.
> 지금은 CSI(Container Storage Interface) 드라이버를 써야 한다.
> 예를 들어 AWS EBS는 `awsElasticBlockStore`대신 `ebs.csi.aws.com`을 사용하며,
> 보통 아래처럼 StorageClass를 통한 동적 프로비저닝으로 다룬다.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-sc
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer
```

> 시험에서는 `hostpath`또는 CSI 기반 StorageClass를 사용한다.

---
## 3. PVC 만들기
PVC를 만들기 전에 클러스터에 사용 가능한 PV가 하나 이상 있어야 한다.
- `apiVersion: v1`, `kind: PersistentVolumeClaim`
- `accessModes`, `resources.requests.storage` 지정

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: myclaim
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 500Mi
```

```bash
kubectl create -f pvc-definition.yaml
kubectl get pvc
# NAME      STATUS    VOLUME   CAPACITY   ACCESS MODES
# myclaim   Pending
```
처음엔 `Pending`상태로, Kubernetes가 조건에 맞는 PV를 찾는 중이다.

---
## 4. 바인딩 - PVC <-> PV
PVC가 생성되면 Kubernetes는 요청 용량과 속성(accessModes, volumeMode, storageClass)이 맞는 PV를 찾아 바인딩한다.
- PVC <-> PV 는 1:1 관계이다. 하나의 PV는 하나의 PVC에만 바인딩된다.
- 용량이 남아도 다른 클레임이 그 남은 용량을 쓸 수 없다.
- 조건에 맞는 PV가 여러 개면, 레이블과 셀렉터로 특정 PV에 바인딩하도록 지정할 수 있다.

```yaml
#PVC
selector:
  matchLabels:
    name: my-pv
```

```yaml
#PV
labels:
  name: my-pv
```

- 다른 조건이 모두 맞고 더 나은 옵션이 없으면, 작은 요청이 더 큰 볼륨에 바인딩될 수 있다.
- 맞는 PV가 없으면 PVC는 `Pending`상태로 남는다. 이후 조건에 맞는 새 PV가 추가되면 자동으로 바인딩된다.

위 예시에서 PV(1Gi, RWO)가 PVC 요청(500Mi, RWO)을 충족하므로, 더 가까운 매치가 없다면 바인딩 되어 상태가 `Bound`로 바뀐다.

```bash
kubectl get persistentvolumeclaim
# myclaim   Bound   pv-vol1   1Gi   RWO
```

---
## 5. PVC 삭제와 Reclaim Policy (반환 정책)
PVC를 삭제하면, 바인딩됐던 PV를 어떻게 처리할지는 PV의 `persistentVolumeReclaimPolicy`가 결정한다.
```bash
kubectl delete psv myclaim
```

**정책**

|정책|동작|
|--|--|
|Retain(default)|PVC가 삭제돼도 PV는 그대로 유지. 관리자가 수동으로 삭제할 때까지 남음. 단 다른 클레임이 재사용할 수는 없음|
|Delete| PVC 삭제 시 PV도 자동 삭제 -> 스토리지 즉시 해제|
