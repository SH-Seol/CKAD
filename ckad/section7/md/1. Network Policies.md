# 1. Network Policies
> kubernetes에서 파드 간 트래픽을 제어하는 NetworkPolicy를 다룬다. 
> 기본적으로 모든 트래픽이 허용되는 클러스터에서, 특정 파드를 보호하여 허가된 소스에만 접근하도록 제한하는 방법을 정리한다.

---
## 1. Ingress & Egress
먼저 트래픽 방향의 기본 개념부터 짚자. 웹서버 -> API 서버 -> DB 서버로 이어지는 간단한 구성을 예로 들자.
- 사용자 -> 웹서버(port 80)
- 웹서버 -> API서버(port 5000)
- API서버 -> DB서버 (port 3306)

여기서 트래픽은 두 방향으로 나뉜다.
- Ingress: 파드로 들어오는 트래픽
- Egress: 파드에서 나가는 트래픽

> 중요: Ingress/Egress는 트래픽이 처음 시작된(발생한) 방향만 기준으로 본다.
> 요청에 대한 응답(response)은 신경 쓰지 않는다.

예를 들어 웹 서버 관점에서 사용자로부터 오는 것은 인그레스, API 서버로 나가는 요청은 이그레스이다.
DB 서버 관점에서는 API 서버로부터 포트 3306으로 들어오는 것이 인그레스이다.

---
## 2. Kubernetes의 기본 네트워킹
- 클러스터의 각 노드, 파드, 서비스는 모두 IP 주소를 가진다.
- Kubernetes 네트워킹의 전제 조건: 추가 라우팅 설정 없이도 모든 파드가 서로 통신 가능해야 함
- 따라서 기본 값은 **모두 허용(All Allow)** - 어떤 파드든 클러스터 내 다른 파드/서비스로 트래픽을 보낼 수 있다.

이 상태에서 웹서버가 DB 서버에 직접 접근하지 못하게 하려면 NetworkPolicy가 필요하다.

---
## 3. NetworkPolicy 동작 원리
- NetworkPolicy는 파드, ReplicaSet, 서비스처럼 네임스페이스에 속하는 오브젝트이다.
- 레이블과 셀렉터로 하나 이상의 파드에 연결된다.
- 정책이 적용되면, 해당 파드로의 다른 모든 트래픽을 차단하고 정책에 명시된 규칙과 일치하는 트래픽만 허용한다.
- 정책은 그 정책이 적용된 파드에만 영향을 준다.

---
## 4. 실습 목표
DB 파드를 보호하여, 오직 API 파드만 포트 3306으로 접근하도록 허용한다.
웹 파드 등 다른 트래픽은 신경 쓰지 않는다.

#### Step 1 - 모든 트래픽 차단 + 대상 파드 선택
DB 파드(`role: db`레이블)에 정책을 연결하기만 해도, 인그레스가 정책 대상이 되어 기본적으로 인그레스가 차단된다.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-policy
spec:
  podSelector:
    matchLabels:
      role: db
  policyTypes:
    - Ingress
```
- `podSelector` -> 이 정책을 적용할 파드 지정(여기선 `role: db`)
- `policyTypes` -> 규칙이 Ingress인지 Egress인지, 아니면 둘 다인지 지정

---

## 5. 특정 인그레스 트래픽 허용
API 파트(`name: api-pod`)에서 포트 3306(TCP)으로 오는 트래픽한 허용하는 인그레스 규칙을 추가한다.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-policy
spec:
  podSelector:
    matchLabels:
      role: db
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              name: api-pod
      ports:
        - protocol: TCP
          port: 3306
```

> **응답은 자동 허용**: 인그레스 트래픽을 허용하면, 그에 대한 응답(reply)은 별도 규칙 없이 자동으로 되돌아간다.
> 그래서 여기서는 인그레스 규칙 하나면 API 파드가 쿼리하고 결과를 받아올 수 있다.
> 단, 이 인그레스 규칙은 DB로 들어오는 트래픽만 다룬다. DB 파드가 먼저 나가는(egress)연결을 시도하는 경우는
> 별도의 egress 규칙이 없으면 차단된다.

---
## 6. 네임스페이스로 제한하기 (namespaceSelector)

레이블이 같은 API 파드가 여러 네임스페이스(dev/test/prod)에 있다면, 위 정책은 모든 네임스페이스의 API 파드를 허용해버린다.
prod 네임스페이스의 API 파드만 허용하려면 `namespaceSelector`를 추가한다.

```yaml
  ingress:
    - from:
        - podSelector:
            matchLabels:
              name: api-pod
          namespaceSelector:
            matchLabels:
              name: prod
      ports:
        - protocol: TCP
          port: 3306
```
- 전제: 네임스페이스에 미리 `name: prod`와 같은 레이블이 지정되어 있어야 namespaceSelector가 작동한다.
- `podSelector`와 `namespaceSelector`가 같은 `-` 항목(같은 규칙)안에 있으면 -> AND 연산:
"api-pod"레이블이면서 동시에 prod 네임스페이스에 있는 파드만 통과
- `namespaceSelector`만 있고 `podSelector가 없으면:
해당 네임스페이스의 모든 파드가 접근 가능 (웹 파드 등 원치 않는 트래픽도 허용될 수 있음).

---
## 7. 외부 소스 허용(ipBlock)
클러스터 외부의 백업 서버(ex. `192.168.5.10`)가 DB에 접근해야 한다면, 파드, 네임스페이스 셀렉터는
클러스터 밖이라 작동하지 않는다. 대신 `ipBlock`으로 IP 대역을 지정한다.
```yaml
spec:
  podSelector:
    matchLabels:
      role: db
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              name: api-pod
          namespaceSelector:
            matchLabels:
              name: prod
        - ipBlock:
            cidr: 192.168.5.10/32
      ports:
        - protocol: TCP
          port: 3306
```

**And vs Or** - 대시(`-`)의 위치가 핵심
`from` 아래 요소를 어떻게 나누느냐로 논리가 완전히 바뀐다.
- 하나의 `-` 항목 안에 여러 셀렉터(ex. podSelector + namespaceSelector) -> AND
- 각 셀렉터를 별도 `-` -> OR

위 예시에서 `from`아래에는 두 개의 요소가 있다.
1. 첫 번째 요소: `podSelector` + `namespaceSelector`(AND) -> "prod 네임 스페이스의 api-pod"
2. 두 번째 요소: `ipBlock` -> 외부 백업 서버 IP

이 두 요소는 서로 OR 관계, 둘 중 하나만 충족해도 DB에 도달할 수 있다.
> 이처럼 대시 하나 차이로 "prod의 api-pod만"이 "prod의 아무 파드나 + IP블록"으로 크게 바뀔 수 있으니 
> 요구사항에 맞춘 규칙 구조 설계가 매우 중요하다.

---
## 8. 이그레스 규칙(Egress)
DB 파드가 먼저 외부로 나가는 트래픽(ex. 백업을 외부 서버로 푸시)을 허용하려면 egress 규칙이 필요하다.
1. `policyTypes`에 `Egress`추가
2. `egress`섹션 추가. 인그레스와 구조는 같지만 `from`대신 `to`를 사용

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-policy
spec:
  podSelector:
    matchLabels:
      role: db
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              name: api-pod
      ports:
        - protocol: TCP
          port: 3306
  egress:
    - to:
        - ipBlock:
            cidr: 192.168.5.10/32
      ports:
        - protocol: TCP
          port: 80
```

이 구성은 기존 인그레스 제한(API -> DB, 3306)을 유지하면서, DB -> 외부 백업서버(port 80)로 나가는 트래픽을 추가로 허용한다.

---
## 9. 정책 생성 & 네트워크 솔루션 주의사항

```bash
kubectl create -f network-policy-definition.yaml
kubectl get networkpolicy # or netpol
```

> 매우 중요: NetworkPolicy는 클러스터에 설치된 네트워크 솔루션(CNI)이 실제로 적용. 그런데 모든 CNI가 NetworkPolicy를 지원하는 것은 아니다.
> - 지원: Kube-router, Calico, Romana, Weave-net 등
> - 미지원(강의 시점): Flannel
> - 더 큰 함정: 미지원 솔루션에서도 정책 생성 자체는 성공하지만 적용되지 않고 경고 에러 메시지가 뜨지 않는다. 
> 지원 여부는 항상 CNI문서를 확인하자.

---
### CKAD 핵심 정리

- 기본값은 all-allow. NetworkPolicy가 파드에 적용되는 순간, 해당 파드는 명시된 규칙 외 트래픽 차단
- `apiVersion: networking.k8s.io/v1`, `kind: NetworkPolicy` - 네임스페이스 스코프 오브젝트
- `podSelector`: 정책을 적용할 대상 파드 선택 (비우면 네임스페이스 내 전체 파드)
- `policyTypes`: `Ingress`, `Egress`, 또는 둘 다. 적어둔 타입만 제어됨
- 응답 트래픽은 자동 허용 -> 요청이 시작되는 방향만 규칙으로 정의하면 됨.
- AND vs OR
  - 하나의 `from` / `to` 항목 안의 여러 셀렉터 = AND
  - 별도 `-`항목으로 분리한 셀렉터 = OR
- 3가지 Selector: `podSelector`, `namespaceSelector`, `ipBlock`. 
ingress `from` / egress `to` 양쪽에서 사용 가능
- `namespaceSelector` 사용 시 네임스페이스에 레이블이 먼저 있어야 함
- `namespaceSelector`만 있고 `podSelector` 없으면 -> 그 네임스페이스 전체 파드 허용.
- egress는 `to`, ingress는 `from` 사용
- 명령어: `kubectl get netpol`, `kubectl describe netpol <name>`.
