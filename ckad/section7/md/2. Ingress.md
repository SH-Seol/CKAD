# 2. Ingress

> 하나의 외부 URL로 애플리케이션에 접근하게 하고, URL 경로나 호스트(도메인)에 따라 클러스터 내 여러
> 서비스로 트래픽을 라우팅하며, SSL까지 한곳에서 처리하는 Kubernetes의 L7 로드밸런서이다.
> Service만으로는 관리가 복잡해지는 문제를 해결한다.

---
## 1. 왜 인그레스가 필요한가? (Service의 한계)
온라인 스토어 앱(`onlinestore.com`)을 배포하는 시나리오로 문제를 따라가 보자.

1. 앱 + DB배포: 앱은 Deployment 안의 Pod로, MYSQL은 Pod로 배포하고 앱이 DB에 접근하도록 ClusterIP타입 서비스를 만든다.
2. 외부 노출(NodePort): 앱을 외부에서 접근하게 하려고 NodePort 서비스를 만든다(ex. port 30080).
-> 사용자는 `http://<노드IP>:30080`으로 접근. 트래픽이 늘면 복제본 수만 늘리면 서비스가 알아서 분산
3. DNS + 프록시: 사용자가 IP, 포트를 기억하지 않도록 DNS를 노드 IP로 연결하고, 포트 80 -> 30080으로 넘겨주는 프록시를 둔다. -> `onlinestore.com`으로 접근
4. 클라우드라면 LoadBalancer: GCP같은 퍼블릭 클라우드에서는 LoadBalancer 타입 서비스를 만들면,
클라우드가 네트워크 로드밸런서를 자동 프로비저닝하고 외부 IP를 돌려준다. DNS를 이 IP로 연결.

**문제가 커지는 지점**
- 새 서비스(ex. `onlinestore.com/watch`)를 추가하면 LoadBalancer가 새로 필요(별도 포트 30081 + 전용 GCP LB) -> 각각 비용 발생, IP도 따로.
- URL 기반으로 여러 로드밸런서 사이에서 트래픽을 나눌 또 다른 프록시가 필요.
- 새 서비스마다 방화벽 규칙, SSL 설정을 여러 곳에서 반복 구성해야 함.

> 이 모든 라우팅, 로드밸런싱, SSL 구성을 클러스터 안에서, 다른 배포 파일들과 함께 있는 하나의 Kubernetes 정의 파일로 관리하고 싶다 -> 인그레스

> 단 인그레스 자체도 외부 노출은 필요하다. 여전히 NodePort, 클라우드 LB로 한 번에 게시해야 하지만, 
> 이는 일회성 구성이고 이후 모든 라우팅/SSL은 인그레스 컨트롤러가 중앙에서 처리

---
## 2. 인그레스의 두 구성 요소
| 구성 요소                         | 역할                                                                            |
|-------------------------------|-------------------------------------------------------------------------------|
| 인그레스 컨트롤러(Ingress Controller) | 실제로 트래픽을 처리하는 리버스 프록시/로드밸런서 (nginx, HAProxy, Traefik 등).클러스터를 감시하며 규칙 변경을 반영. |
| 인그레스 리소스(Ingress Resource)    | 라우팅 규칙, SSL 설정을 담은 YAML 정의. Pod/Deployment/Service처럼 생성.                      |

> **매우 중요**: Kubernetes 클러스터에는 기본적으로 인그레스 컨트롤러가 없다. 
> 인그레스 리소스만 만들고 컨트롤러가 없으면 작동하지 않으므로 컨트롤러를 먼저 배포해야 한다.

인그레스 컨트롤러 솔루션
GCP HTTP(S) LB(GCE), nginx, Contour, HAProxy, Traefik, Istio 등. 이 중 GCP, nginx가 Kubernetes 프로젝트에서 공식 지원, 유지 보수된다.

## 3. 인그레스 컨트롤러 배포 (nginx 예시)
단순한 nginx 서버가 아니라, 인그레스 리소스를 감시해 nginx 설정을 자동 갱신하는 추가 지능이 들어 있다.
배포에 필요한 4가지 구성 요소:
1. **Deployment**
nginx 인그레스 컨트롤러 이미지(전용 빌드). ConfigMap을 인자로 받고, 자신의 Pod 이름/네임스페이스를 환경 변수로 받으며, 포트 80/443을 노출한다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-ingress-controller
spec:
  replicas: 1
  selector:
    matchLabels:
      name: nginx-ingress
  template:
    metadata:
      labels:
        name: nginx-ingress
    spec:
      containers:
        - name: nginx-ingress-controller
          image: quay.io/kubernetes-ingress-nginx/controller
          args:
            - /nginx-ingress-controller
            - --configmap=$(POD_NAMESPACE)/nginx-configuration
          env:
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            - name: POD_NAMESPACE
              valueFrom:
                fieldRef:
                  fieldPath: metadata.namespace
          ports:
            - name: http
              containerPort: 80
            - name: https
              containerPort: 443
```

2. **ConfigMap**
nginx 설정(로그 경로, keep-alive, SSL, 세션 타임아웃 등)을 이미지와 분리해 관리.
처음엔 비어 있어도 되고, 나중에 항목만 추가하면 nginx 설정 파일을 직접 안 건드려도 된다.
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-configuration
```

3. **Service**
컨트롤러 외부에 노출. `nginx-ingress`레이블 셀렉터로 Deployment에 연결.
```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-ingress
spec:
  type: NodePort
  ports:
    - port: 80
      targetPort: 80
      protocol: TCP
      name: http
    - port: 443
      targetPort: 443
      protocol: TCP
      name: https
  selector:
    name: nginx-ingress
```

4. **ServiceAccount (+ Role, RoleBinding)
컨트롤러가 클러스터의 인그레스 리소스를 모니터링할 수 있도록 권한 부여

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: nginx-ingress-serviceaccount
```
> 요약: Deployment + Service + ConfigMap + ServiceAccount이 갖춰지면 가장 단순한 형태의 인그레스 컨트롤러가 준비된다.

## 4. 인그레스 리소스 생성
인그레스 리소스는 컨트롤러에 라우팅 규칙을 알려주는 정의이다. 흔히 3가지 시나리오가 있다.

**(A) Default Backend - 규칙 없이 전부 한 서비스로**
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-wear
spec:
  defaultBackend:
    service:
      name: wear-service
      port:
        number: 80
```

```bash
kubectl create -f Ingress-wear.yml
kubectl get ingress
# NAME           CLASS    HOSTS    ADDRESS    PORTS   AGE
# ingress-wear   <none>   *        <none>     80      2s
```

**(B) 경로 기반 라우팅(Path-Based) - 규칙 1개 + path 여러 개**
같은 도메인에서 URL 경로로 나눌 때(`/wear`, `/watch`). 각 path에는 `pathType`이 반드시 있어야 한다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-wear-watch
spec:
  rules:
    - http:
        paths:
          - path: /wear
            pathType: Prefix
            backend:
              service:
                name: wear-service
                port:
                  number: 80
          - path: /watch
            pathType: Prefix
            backend:
              service:
                name: watch-service
                port:
                  number: 80
```
```bash
kubectl describe ingress ingress-wear-watch
```

**(C) 호스트 기반 라우팅 (Host-Based) - 도메인마다 규칙 1개**
도메인이 여러 개일 때(`wear.ostore.com`, `watch.ostore.com`). 각 규칙에 `host` 지정.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ingress-host-based
spec:
  rules:
    - host: wear.online-store.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: wear-service
                port:
                  number: 80
    - host: watch.online-store.com
      http:
        - paths:
            - path: /
              pathType: Prefix
              backend:
                service:
                  name: watch-service
                  port:
                    number: 80
```
> `host`필드를 생략하면 모든 호스트(*)의 트래픽에 규칙이 적용된다.

**매칭되지 않는 트래픽 처리**
어떤 규칙에도 안 맞는 요청(ex.`online-store.com/listen`)은 defaultBackend(`spec.defaultBackend`)로 보낸다.
여기에 404페이지용 서비스를 배포해 두면 사용자에게 적절한 응답을 줄 수 있다.

---
## 5. 경로(path) vs 호스트(host)
| 방식        | 규칙(rule) 수 | 경로(path)       | 언제                                  |
|-----------|------------|----------------|-------------------------------------|
| URL 경로 기반 | 1개         | 규칙 안에 여러 path  | `store.com/wear`, `store.com/watch` |
| 호스트 기반    | 도메인 수만큼    | 각 규칙에 보통 1path | `wear.store.com`, `watch.store.com`  |

---
## 6. 명령형(Imperative) 생성 - _k8s 1.20+_
인그레스를 명령어로 바로 만들 수 있다. 시간 아끼는 용도로 기억해두자.

```bash
kubectl create ingress <ingress-name> --rule="host/path=service:port"
```

- 경로 뒤의 `*`(ex. `/wear*`)는 `pathType: Prefix`를 의미한다. (`*` 없으면 `Exact`)
- 여러 규칙은 `--rule`을 여러 번 붙여서 지정한다.

---
### CKAD 핵심 정리
- 인그레스 = L7(HTTP/HTTPS)라우팅 + SSL 종료 + 로드밸런싱을 클러스터 내부 리소스 하나로 관리
- 두 부분: 인그레스 컨트롤러(직접 배포, ex: nginx), 인그레스 리소스(규칙 YAML).
- 컨트롤러는 기본 미포함 -> 별도 배포 필요. 리소스만 만들면 동작 안함
- 인그레스도 외부 노출을 위해 NodePort/LoadBalancer로 한 번 게시 필요
- 컨트롤러 배포 4종: Deployment + Service(NodePort) + ConfigMap + ServiceAccount(+Role/RoleBinding)
- 트래픽은 Service로 라우팅됨(Not Pod)
- 라우팅 3형태: Default backend / 경로 기반(1 rule, lots of path) / 호스트 기반 (1 rule per domain)
- 매칭 안 되는 트래픽 -> default backend(404 페이지 등). 해당 서비스도 배포해야 함.
- 명령형 생성: `kubectl create ingress <name> --rule=host/path*=service:port` - `*`는 `Prefix`
- 명령어 `kubectl get ingress`, `kubectll describe ingress <name>`.
