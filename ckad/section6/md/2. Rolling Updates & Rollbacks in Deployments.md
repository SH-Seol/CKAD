# Rolling Updates & Rollbacks

> Kubernetes Deployment에서 애플리케이션 업데이트와 롤백이 어떻게 동작하는지 다룬다.
> rollout, version, deployment strategy를 이해하고 다운타임을 최소화하며 업그레이드를 관리하는 것이 목표.

---
## 1. Rollouts & Versioning
- Deployment를 처음 생성하면 rollout이 트리거 되고, 첫 번째 배포 리비전인 revision 1이 만들어진다.
- 이후 애플리케이션을 업데이트하면(ex. 컨테이너 이미지 버전 변경) 새 rollout이 발생하고, revision2라는 새 revision이 생성된다.
- 이 구조로 변경 사항을 추적할 수 있고 필요하면 이전 버전으로 rollback이 가능하다.

#### 롤 아웃 상태 확인

```bash
kubectl rollout status deployment/myapp-deployment
```

출력 예시:
```bash
Waiting for rollout to finish: 0 of 10 updated replicas are available...
Waiting for rollout to finish: 1 of 10 updated replicas are available...
...
Waiting for rollout to finish: 9 of 10 updated replicas are available...
deployment "myapp-deployment" successfully rolled out
```

#### revision 이력 확인
```bash
kubectl rollout history deployment/myapp-deployment
```

## 2. 배포 전략(Deployment Strategies)
Kubernetes는 두 가지 주요 배포 전략을 지원한다.(ex. 복제본 5개를 새 버전으로 업그레이드하는 상황)

1. Recreate 전략(다시 만들기)
    - 기존 인스턴스(5개)를 모두 한번에 종료한 뒤, 새 버전 인스턴스(5개)를 새로 생성
    - 단점: 다운 타임 발생, 이전 버전 내려가고 새 버전 올라오기 전까지 애플리케이션에 접근할 수 없다.
    - 기본값이 아닌 전략
2. Rolling Update 전략(롤링 업데이트)
    - 한 번에 전부 죽이지 않고, 이전 버전을 하나씩 내리면서 새 버전을 하나씩 올린다.
    - 업그레이드 중에도 애플리케이션이 계속 사용 가능하여 다운타임이 없다.
    - **기본 전략**

## 3. Deployment 업데이트 방법
"업데이트"는 컨테이너 이미지 버전 변경, 레이블 변경, 복제본 수 변경 등 다양한 것을 의미할 수 있다. 업데이트하는 방법은 두 가지이다.
1. definition file 수정 후 apply
정의 파일을 직접 수정한 뒤 적용. 새 rollout이 트리거되고 새 revision이 생성
```bash
kubectl apply -f deployment-definition.yml
```

2. set image로 이미지만 변경
```bash
kubectl set image deployment/myapp-deployment nginx=nginx:1.9.1
```
> `kubectl set image`는 실행 중인 구성만 바꾸기 때문에, deployment-definition.yml의 내용과 달라진다.
> 나중에 같은 정의 파일로 변경 작업을 할 때 혼란이 생기므로, 정의 파일도 함께 업데이트해야 한다.

#### Deployment definition file 예시

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-deployment
  labels:
    app: myapp
    type: front-end
spec:
  replicas: 3
  selector:
    matchLabels:
      type: front-end
  template:
    metadata:
      name: myapp-pod
      labels:
        app: myapp
        type: front-end
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.7.1
```

## 4. Deployment 상세 확인 - 두 전략의 차이

`kubectl describe`로 보면 두 전략의 동작 차이를 Events에서 확인 가능하다.

```bash
kubectl describe deployment myapp-deployment
```

#### Recreate 전략의 동작
이전 ReplicaSet이 먼저 0으로 축소(scale down)된 뒤, 새 ReplicaSet이 5로 확장된다.

```text
StrategyType:          Recreate
...
Events:
  Normal  ScalingReplicaSet  11m   deployment-controller Scaled up replica set ...-6795844b58 to 5
  Normal  ScalingReplicaSet  1m    deployment-controller Scaled down replica set ...-6795844b58 to 0
  Normal  ScalingReplicaSet  56s   deployment-controller Scaled up replica set ...-54c76dccc to 5
```

#### Rolling Update 전략의 동작
이전 ReplicaSet이 한 번에 하나씩 축소되는 동시에 새 ReplicaSet이 한 번에 하나씩 확장된다.

```text
StrategyType:          RollingUpdate
MinReadySeconds:       0
RollingUpdateStrategy: 25% max unavailable, 25% max surge
...
Events:
  Normal  ScalingReplicaSet  1m    deployment-controller Scaled up replica set ...-67c749c58c to 5
  Normal  ScalingReplicaSet  15s   deployment-controller Scaled down replica set ...-67c749c58c to 4
  Normal  ScalingReplicaSet  0s    deployment-controller Scaled up replica set ...-75d78bd8d to 3
  Normal  ScalingReplicaSet  0s    deployment-controller Scaled down replica set ...-67c749c58c to 0
```

> 롤링 업데이트는 이전 -> 새 ReplicaSet으로 점진적으로 전환하여 가용성을 유지한다.

## 5. 내부 동작 원리
- Deployment를 생성하면 Kubernetes가 자동으로 ReplicaSet을 생성하고, 그 ReplicaSet이 Pod들을 관리한다.
- 업그레이드 시에는 새 구성을 위한 새 ReplicaSet이 생성되고, 이전 ReplicaSet은 그 set의 pod를 제거한다.

```bash
kubectl get replicasets
```

> Pod가 0개인 이전 ReplicaSet과 원하는 수만큼 pod를 가진 새 replicaSet이 함께 보인다.

## 6. Rollback
업그레이드 후 새 빌드에 문제가 있다면 이전 버전으로 되돌아갈 수 있다.

```bash
kubectl rollout undo deployment/myapp-deployment
```

이 명령은 새 ReplicaSet의 pod를 제거하고 이전 ReplicaSet의 Pod를 다시 가져와 애플리케이션을 이전 상태로 복원한다.
롤백 전후로 ReplicaSet의 Pod수가 역전되는 것을 볼 수 있다.

#### 이전
```bash
kubectl get replicasets
NAME                        DESIRED   CURRENT   READY   AGE
myapp-deployment-67c749c58c  0         0         0       22m
myapp-deployment-7d57dbd8d   5         5         5       20m
```

#### 이후
```bash
kubectl get replicasets
NAME                        DESIRED   CURRENT   READY   AGE
myapp-deployment-67c749c58c  5         5         5       22m
myapp-deployment-7d57dbd8d   0         0         0       20m
```

#### undo 실행 시 출력
```text
deployment "myapp-deployment" rolled back
```

## 7. 명령어 요약(Quick Reference)

| 명령어                                                               | 설명                        |
|-------------------------------------------------------------------|---------------------------|
| `kubectl create -f deployment-definition.yml`                     | 새 Deployment 생성           |
| `kubectl get deployments`                                         | Deployment 목록 조회          |
| `kubectl apply -f deployment-definition.yml`                      | 정의 파일 변경 사항 적용            |
| `kubectl set image deployment/myapp-deployment nginx=nginx:1.9.1` | Deployment의 컨테이너 이미지 업데이트 |
| `kubectl rollout status deployment/myapp-deployment`              | 롤아웃 진행 상태 확인              |
| `kubectl rollout undo deployment/myapp-deployment`                | 이전 리비전으로 롤백               |


### CKAD 핵심 정리
- Deployment 생성 / 업데이트 시마다 새 rollout + 새 리비전이 생성됨 -> 추적, 롤백 가능
- 배포 전략
  - Recreate: 전부 종료 후 재생성 -> 다운타임 있음
  - RollingUpdate: 하나씩 교체 -> 무중단, 그리고 기본 전략
- RollingUpdate 기본 파라미터: `25% max unavailable, 25% max surge`
- 업데이트 방법: `kubectl apply -f`(권장) / `kubectl set image` (definition 파일과 어긋남) / `kubectl edit`
- 롤아웃 상태 / 이력: `kubectl rollout status`, `kubectl rollout history`
- `--revision=N`: 특정 리비전의 상세(Pod템플릿, 이미지)확인
- `--record`: 실행 명령을 `CHANGE-CAUSE`(=`kubernetes.io/change-cause` 어노테이션)에 기록(현재는 deprecated)
- 롤백
  - `kubectl rollout undo deployment/<name>` -> 직전 리비전으로
  - `kubectl rollout undo deployment/<name> --to-revision=N` -> 특정 리비전으로
- 롤백 확인 팁: `kubectl describe deployment <name> | grep -i image:`로 현재 이미지 버전 빠르게 확인
- 업그레이드는 내부적으로 새 ReplicaSet 생성 <-> 이전 ReplicaSet 축소로 이루어짐
- 진행 중 롤아웃 일시정지/재개: `kubectl rollout pause` / `kubectl rollout resume`
