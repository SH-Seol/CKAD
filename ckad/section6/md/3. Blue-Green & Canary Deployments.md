# 배포전략: Blue-Green & Canary Deployments

> 앞서 다룬 Recreate와 Rolling Update 전략에 이어, Kubernetes의 기본 primitive만으로 구현할 수 있는 추가 배포 전략인
> Blue-Green 과 Canary를 정리한다. 둘 다 업데이트 중 위험과 다운타임을 줄이는 것이 목적이다.

---
## 복습
| 전략               | 동작                          | 특징         |
|------------------|-----------------------------|------------|
| `Recreate`       | 기존 버전을 모두 종료한 뒤 새 버전 생성     | 다운타임 발생    |
| `Rolling Update` | 이전 버전을 하나씩 내리며 새 버전을 하나씩 올림 | 무중단, 기본 전략 |

> Blue-Green과 Canary는 Deployment의 `strategy`필드로 지정하는 옵션이 아니다.
> Deployment와 Service를 조합해 직접 구현하는 패턴이다.

---
## 1. Blue-Green Deployment
두 개의 프로덕션 환경을 동시에 운영하는 전략
- Blue 환경: 현재 운영 중인 안정(stable) 버전
- Green 환경: 새로 준비, 테스트 중인 신규 버전

처음에는 트래픽 100%가 Blue로 간다. Green을 띄워 충분히 테스트, 검증한 뒤, 단 한번의 변경으로 트래픽을 Green으로 전환한다.
살아있지만 격리된 환경에서 신규 릴리즈를 미리 검증할 수 있어 위험이 줄어든다.

> Istio같은 서비스 메시로 더 세밀하게 제어할 수 있다.

**동작방식 (3단계)**

1. Blue 버전 배포(현재 프로덕션): 원본 버전을 `version: v1`레이블로 배포하고, 이 레이블을 가리키는 셀렉터를 가진 Service를 생성 -> 모든 트래픽이 Blue Pod로 라우팅됨
2. Green 버전 배포(신규 릴리즈): 새 버전을 별도 Deployment로 배포하고 Pod에 `version: v2`레이블 부여. Blue, Green 동시에 실행되지만, Service는 여전히 `v1`만 가리키므로 트래픽은 Blue로만 감
3. 테스트 후 트래픽 전환: Green이 안정적임을 확인하면, Service의 셀렉터를 `v1` -> `v2`로 변경. 이 한번의 변경으로 전체 트래픽이 Green Pod로 전환됨.

**코드 예시**

처음에 Blue(v1)로 트래픽을 보내는 Service

```yaml
# service-definition.yml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    version: v1
```

Blue 버전 Deployment

```yaml
# myapp-blue.yml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-blue
  labels:
    app: myapp
    type: front-end
spec:
  replicas: 5
  selector:
    matchLabels:
      version: v1
  template:
    metadata:
      labels:
        version: v1
    spec:
      containers:
        - name: app-container
          image: myapp-image:1.0
```

Green 버전은 위와 비슷하게 만들되 이미지를 `myapp-image:2.0`으로, 레이블을 `version: v2`로 지정.
테스트 완료 후, Service의 셀렉터만 v2로 바꾸면 전환이 끝난다.

```yaml
# 트래픽을 Green(v2)로 전환하도록 업데이트한 service-definition.yml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    version: v2
```

## 2. Canary Deployment
신규 버전을 기존 버전과 함께 배포하되, 소량의 트래픽만 신규 버전으로 보내는 전략. 프로덕션에서 새 기능을 테스트하면서 위험을 최소화한다.
검증이 끝나면 주(primary)배포를 새 버전으로 업그레이드하고 카나리는 제거한다.

**핵심 3단계**
1. 하나의 Service로 두 배포 모두에 트래픽 라우팅 -> 공통 레이블(ex. `app: front-end`)사용
2. 카나리 배포의 replica 수를 낮게(ex. `replicas: 1`)설정 -> 신규 버전(v2)으로 가는 트래픽 비율을 작게 유지
3. 테스트 성공 시 -> 주 배포를 새 버전으로 업그레이드하고 카나리 배포 제거.

**코드 예시**

```yaml
#myapp-primary.yml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-primary
  labels:
    app: myapp
    type: front-end
spec:
  replicas: 5
  selector:
    matchLabels:
      app: front-end
  template:
    metadata:
      labels:
        version: v1
        app: front-end
    spec:
      containers:
        - name: app-container
          image: myapp-image:1.0

---

#service-definition.yml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: front-end

---
#myapp-canary.yml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-canary
  labels:
    app: myapp
    type: front-end
spec:
  replicas: 1
  selector:
    matchLabels:
      app: front-end
  template:
    metadata:
      labels:
        version: v2
        app: front-end
    spec:
      containers:
        - name: app-container
          image: myapp-image:2.0
```

이 구성의 핵심
- 주 배포(`myapp-primary`): v1, 복제본 5개
- Service(`my-service`): 공통 레이블 `app: front-end`를 셀렉터로 사용 -> 두 배포의 Pod를 모두 잡음
- 카나리 배포(`myapp-canary`): v2, 복제본 1개 -> 소량의 트래픽만 v2로

> 핵심 트릭: 두 배포의 Pod가 공통 레이블(`app: front-end`)을 공유하므로 하나의 Service가 둘 다에 트래픽을 보내고,
> 버전 구분(`version: v1`/`v2`)레이블은 식별용으로 따로 둔다.

---
### CKAD 핵심 정리
- Blue-Green / Canary는 Deployment의 `strategy`옵션이 아니다. Deployment + Service 조합으로 직접 구현하는 패턴
- Blue-Grren:
  - Blue(v1), Green(v2)을 동시에 운영, 트래픽은 처음엔 100% Blue
  - 전환은 Service의 셀렉터를 `v1` -> `v2`로 변경하는 단 한번의 작업
  - 장점: 격리된 환경에서 사전 검증, 즉시 전환/롤백 용이. 단점 두 환경분 리소스 필요.
- Canary:
  - 하나의 Service가 공통 레이블(`app: front-end`)로 주 + 카나리 양쪽 Pod에 트래픽 분배.
  - 트래픽 비율 = Pod 수 비율(ex. 5:1 -> 약 83% : 17%)
  - 정밀 비율 제어는 순수 k8s로는 한계 -> Istio 등 서비스 메시 필요.
- 전략 자체보다 Service 셀렉터와 Pod 레이블의 매칭 관계를 정확히 구성하자.
